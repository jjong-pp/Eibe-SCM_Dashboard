# qa-review

## 준비
1. 계약서 `.squad/contracts/T-###.md`를 읽는다 (목표, 수용 기준, 범위 밖)
2. `git diff <base> --stat`로 바뀐 영역을 확인한다. 코드는 수정하지 않는다
3. `python scripts/squad.py qa-server start` → http://127.0.0.1:8765 (admin/admin, 고정 시드 DB). 끝나면 `stop`
4. `python scripts/verify.py --tests` 결과를 기록한다

## 탐색
- 차터 한 줄: "[대상]을 [수단]으로 탐색해 [위험]을 찾는다"
- 브라우저 도구가 있으면 실제 화면을 조작하고 스크린샷을 `.squad/artifacts/T-###/`에 저장한다. 없으면 API 호출과 HTML/JS 분석으로 대신하고 리포트에 적는다
- 바꿔볼 것 (SFDIPOT)
  - 구조: 변경된 컴포넌트와 이웃 컴포넌트
  - 기능: 수용 기준 하나씩
  - 데이터: null, 0, 음수, 긴 문자열, 빈 목록, 대량 행
  - 플랫폼: 다크모드, 폭 1280px 이하, 백엔드 중단
  - 운영: 실무 순서 (아침 위기 확인 → 원인 화면 → 조치)
  - 시간: 월말, 연말, 주차 경계
- 판정 기준 (HICCUPPS): 기존 화면과의 일관성, AGENTS.md·계약서의 주장, 사용자 기대, 같은 종류 B2B 대시보드의 관례
- 최소 확인: 수용 기준 전부, 변경 화면의 다크모드, 백엔드 중단 시 표시

## 루브릭 (항목당 1~5점)
| # | 항목 | 가중치 | 통과 | 확인 |
|---|---|---|---|---|
| R1 | 업무 정확성 | 25 | 4 이상 | 재고일수, 히트맵 구간(6/9/13주), 6개월 리드타임, 실결제 원가 기준 |
| R2 | 데이터 방어 | 20 | 4 이상 | null, 빈 목록, 긴 문자열, 백엔드 중단 |
| R3 | 업무 효율 | 20 | 3 이상 | 핵심 업무 완료까지 클릭 수·화면 이동 수 |
| R4 | 사용성 | 15 | 3 이상 | Nielsen: 상태 표시, 오류 방지, 일관성, 기억보다 인지 |
| R5 | 디자인 시스템 | 10 | 3 이상 | CSS 변수, 다크모드, SVG 아이콘, 표 정렬, 주차·날짜 표기 |
| R6 | 성능 | 10 | 3 이상 | 목록 API 300ms 이하면 5점 기준, 첫 화면 렌더 |

점수: 5 결함 없음 / 4 S4만 / 3 S3 있음 / 2 S2 있음 / 1 S1 있음.
변경과 무관한 항목은 N/A로 두고 가중치에서 뺀다.

## 심각도
- S1 차단: 기능 불가, 잘못된 숫자, 데이터 손실
- S2 주요: 우회는 되지만 업무에 지장
- S3 경미: 불편하지만 업무 가능
- S4 외관

## 판정
- 항목 하나라도 통과 기준 미달이면 FAIL. S1이 하나라도 있으면 FAIL. 가중 평균으로 상쇄하지 않는다
- 찾은 결함의 심각도를 낮추려면 근거를 적는다
- 증거(스크린샷 경로, 명령 출력, 파일:줄) 없는 점수는 쓰지 않는다
- 계약 범위 밖 결함은 FAIL 사유로 삼지 않고 "범위 밖 발견"에 적는다

## 리포트 형식
마지막 메시지로 아래 전문을 출력한다. squad.py가 `.squad/reports/T-###-review.md`로 저장한다.

~~~
# T-### Review
판정: PASS | FAIL
엔진: codex | claude (빌더와 다른 계열: 예/아니오)
차터: ...
검증 명령 결과: verify --tests 통과/실패

## 점수
| 항목 | 점수 | 근거 |
|---|---|---|
| R1 업무 정확성 | 4 | ... |
가중 점수: x.x / 5

## 결함

|---|---|---|---|---|---|

## 개선 요구 (우선순위순, PM 전달용)
1. ...

## 범위 밖 발견
- ...
