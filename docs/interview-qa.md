## 0. 먼저 외울 것

### 0.1 30초 소개

> 사내 SCM 담당자들이 엑셀과 메일로 맞춰 보던 발주·입고·재고·판매 데이터를 한곳에 모으고,
> "이 품목이 몇 주 버티는지, 언제 얼마나 발주해야 하는지"를 사칙연산 통계로 보여주는 사내 플랫폼입니다.
> 처음에는 PC 한 대에서 도는 SCM 대시보드(v1)로 만들었고, 지금은 따로 있던 매출 대시보드와 합쳐
> **판매 원장 하나에서 재고 지표를 파생**시키는 구조로 다시 만들고 있습니다(v2).
> v2 백엔드는 FastAPI와 SQLAlchemy로 API 61개, 테스트 385개까지 와 있습니다.

### 0.2 2분 소개 (문제 → 접근 → 판단 → 결과 → 배운 점)

1. **문제**: 발주·인보이스·입고가 엑셀로 메일을 오갔고, 재고가 몇 주 버티는지 바로 답할 수 없었습니다. 그 결과가 품절, 악성 재고, 유통기한 폐기였습니다.
   게다가 재고를 보는 앱과 매출을 보는 앱이 같은 판매 데이터를 따로 들고 있었습니다.
2. **접근**: 두 앱을 하나의 DB로 합치고, 판매 원장 하나에서 주차별 집계를 **재계산(파생)** 하게 했습니다. 동기화할 대상을 없앤 겁니다.
3. **판단 세 가지**
   - 예측은 머신러닝 대신 **12주 평균 + 감모 버퍼**. 발주 근거를 실무자가 손으로 따라갈 수 있어야 해서입니다
   - 금액·날짜·제약조건 같은 **데이터 규약을 테스트로 강제**했습니다. SQLite에서 금액이 조용히 반올림되는 걸 실측으로 발견한 뒤입니다
   - 인증을 기본값으로 바꿨습니다. v1에서는 계정 목록 API가 무인증으로 열려 있었습니다
4. **결과**: v2 백엔드가 Phase 4까지 완료, 테스트 385개 중 380개 통과. 실패 5개는 원인을 확인했습니다. [직접 채우기: 실사용·업무 효과]
5. **배운 점**: 단위 테스트 141개가 다 통과한 상태에서 실데이터로 돌리니 수요가 음수로 나왔습니다.
   "데이터 없음"을 0으로 덮어쓴 버그였고, 그 뒤로 기능이 끝나면 **실데이터로 전 구간을 돌리고 숫자를 눈으로 보는 것**을 규칙으로 삼았습니다.

### 0.3 숫자 치트시트

| 항목 | 값 |

### 0.4 용어 한 줄 정의

| 용어 | 뜻 |
|---|---|
| 재고일수 (Weeks of Supply) | 현재고 ÷ 주간 수요. 지금 재고로 몇 주 버티는가 |
| 리드타임 | 발주부터 입고까지 걸리는 시간. 이 회사는 해상 운송이라 약 6개월 |
| FEFO | First Expired, First Out. 기한이 이른 로트부터 출고 |
| MOQ | 최소 발주(이관) 수량. 이 배수로만 주문한다 |
| TU / 카툰 입수량 | 한 상자에 든 낱개 수. 발주는 상자 단위라 제안 수량을 이 배수로 올림 |
| HUB / FFC | 용인 메인창고 / 풀필먼트 센터(온라인·오프라인·바이아웃). 이관은 HUB → FFC |
| 평탄화 상수 | 최근 12주 출고량 평균. 일시적 스파이크를 누른 기준 소진율 |
| 감모 버퍼 | 출고량 - 판매량의 평균. 파손·분실·미기록 이관처럼 판매로 설명 안 되는 감소 |
| ISO 주차 | 월요일 시작, 그 해 첫 목요일이 든 주가 1주차. 연말·연초에 달력 연도와 어긋남 |
| 이중 제출 쿠키 | CSRF 방어. JS가 읽을 수 있는 쿠키 값을 헤더로 되돌려 보내게 하고 서버가 둘을 비교 |
| 멱등 | 몇 번을 실행해도 결과가 같다 |
| 낙관적 잠금 | 충돌이 드물다고 보고 잠그지 않되, 저장할 때 버전이 바뀌었으면 거부 |
| WAL | SQLite 저널 모드. 쓰기 중에도 읽기를 막지 않는다 |
| PITR | Point-In-Time Recovery. 관리형 DB의 시점 복구 |

### 0.5 답변 원칙

- **과장하지 않는다.** 꼬리 질문 두 번이면 드러난다. "아직 안 했습니다, 한다면 이렇게 하겠습니다"가 더 강하다
- **한계를 먼저 말한다.** 16절의 약점은 면접관이 찾기 전에 꺼내면 "자기 코드를 정확히 아는 사람"이 된다
- **숫자와 사례로 말한다.** "정밀도 문제가 있었다"보다 "`999999999999999.99`를 넣었더니 `1000000000000000.00`이 나왔다"
- **결정에는 대안과 버린 이유를 붙인다.** "X를 썼다"가 아니라 "X와 Y를 놓고 이런 이유로 X"

## 1. 프로젝트 개요와 동기

### Q1-1. 어떤 프로젝트인가요?
0.1의 30초 소개로 답한다. 이어서 "v1 화면을 보여드릴까요, v2 구조를 설명드릴까요?"로 면접관이 관심 있는 쪽을 고르게 한다.

### Q1-2. 어떤 문제를 풀려고 했나요?
세 가지입니다.
1. **데이터 파편화** — 발주·생산·인보이스·입고가 엑셀로 메일을 오가고 손으로 맞췄습니다. 재고가 몇 주 버티는지 바로 답할 수 없었습니다
2. **같은 사실의 이중 보관** — 재고 앱(SCM)과 매출 앱(Sales Hub)이 판매 데이터를 따로 갖고 있어서, 합치려면 양방향 동기화가 필요했습니다
3. **감에 의존한 발주** — 6개월 뒤 도착분을 지금 주문해야 하는데, 근거가 담당자의 경험뿐이었습니다

### Q1-3. 사용자는 누구고, 실제로 쓰이고 있나요?
**[직접 채우기]** 사용 팀·인원·기간. 실사용 전이라면 이렇게 말한다:
> 아직 정식 운영 전입니다. 대신 실무 엑셀 양식과 같은 형식으로 시드 데이터를 만들어 전 구간을 검증했고,
> 시드가 업무의 정상 경로를 실제로 지나가는지까지 확인했습니다(P-17).

### Q1-4. 성과를 수치로 말할 수 있나요?
**[직접 채우기]** 엑셀 취합 시간, 발주 검토 시간, 품절·폐기 건수처럼 측정한 것이 있으면 그것만 말한다. 없으면:
> 업무 효과는 아직 측정하지 못했습니다. 측정한다면 품절 주차 수, 폐기 금액, 발주 검토에 드는 시간을 도입 전후로 보겠고,
> 예측 자체는 과거 데이터로 백테스트해서 오차(MAE)와 편향을 단순 기준(직전 주 그대로)과 비교하겠습니다.

### Q1-5. 본인 역할은 무엇이었나요? 혼자 했나요?
**[직접 채우기]** 실제 비중대로. AI를 쓴 부분은 숨기지 않는다 (14절). 말할 수 있는 축:
- 업무 규칙 정의 (13주 적정, 6개월 리드타임, HUB→FFC 이관, 유통기한/보증기한 치환)
- 설계 결정과 근거 (D1~D17) — 무엇을 버렸는지까지
- 검증 — 실데이터 전 구간 실행, 빈 클론 재현, 실패 원인 추적

### Q1-6. 왜 v1을 고치지 않고 새로 만들었나요?
바뀌는 게 **데이터 모델 자체**였기 때문입니다.
- 금액 `Float`→`Numeric`, 날짜 `Text`→`Date`, 대문자 테이블명 → 소문자, 두 앱의 테이블 통합. 거의 모든 테이블이 바뀝니다
- v1에는 마이그레이션 도구가 없었습니다(`create_all()`만). 점진적으로 바꿀 안전장치가 없었습니다
- 보안 기본값(하드코딩 시크릿, `admin/admin`, 무인증 조회)도 구조 문제였습니다

그래서 `eibe/` 폴더에 새로 짓고 v1은 그대로 돌게 뒀습니다. 시작 전에 Sales Hub 원본부터 커밋해 안전망을 만들었습니다(Phase 0).
→ **전환 기간에 두 벌을 유지하는 비용은?** v1에는 기능을 더하지 않고 참고용으로만 둡니다. 완료되면 루트로 승격하고 폐기합니다(Phase 7).
→ **폴더 이름은 왜 `eibe`?** `platform`은 Python 표준 라이브러리 모듈명이라 import를 가릴 수 있어서입니다(D10).

### Q1-7. v2 Phase 0~4가 커밋상 이틀(8/13~14)인데 가능한가요?
AI 코딩 도구를 적극적으로 썼습니다. 다만 무엇을 만들지와 맞는지 판단하는 건 제 몫이었습니다.
설계 결정은 STATE.md에 근거와 함께 남겼고, 실데이터 실행에서 나온 문제는 patterns.md에 남겼습니다.
**[직접 채우기]** 설계·리뷰에 들인 실제 시간, 그 전에 v1으로 업무를 익힌 기간(2026-06~07).
→ 14절 답변으로 이어진다.

## 2. 아키텍처와 기술 선택

### Q2-1. 전체 구조를 설명해 주세요.
단일 FastAPI 앱이고 계층이 셋입니다.
- **라우터**: 권한 가드, Pydantic 입력 검증, 응답 직렬화만 합니다
- **서비스**: 업무 계산. 결과와 함께 **근거가 되는 중간값**(평탄화 상수, 감모 버퍼, 주간 수요)을 dataclass로 돌려줍니다
- **모델**: 테이블, 제약조건, 공용 타입

예측 공식(`forecasting.py`)은 DB를 모르는 순수 함수라 DB 없이 테스트합니다. 데이터는 엑셀 업로드 → 판매 원장·재고 스냅샷·입고 → 주차 집계 파생 → 예측 → 화면 순으로 흐릅니다.

### Q2-2. 왜 FastAPI인가요? Django나 Spring은요?
- Pydantic으로 입력 검증과 응답 스키마가 선언 한 번에 끝나고, OpenAPI 문서가 자동으로 나옵니다
- **의존성 주입**이 권한 설계에 그대로 맞았습니다. 라우터 단위로 `Depends(require_operator)`를 걸면 소속 라우트 전부에 적용됩니다
- Django의 admin·ORM·템플릿은 필요 없었습니다. ORM은 SQLAlchemy + Alembic으로 충분했습니다
- 엑셀 처리가 업무의 중심이라 openpyxl 같은 Python 생태계가 맞았습니다
- **[직접 채우기]** 팀·회사의 기존 기술 스택이 영향을 줬다면 그것도

→ **async를 안 쓰던데?** 핸들러가 `def`라 FastAPI가 스레드풀에서 돌립니다. 계산이 가볍고 DB 하나만 보는 구조라 async 이점이 작고, SQLite는 async 드라이버의 이점도 없습니다. 외부 API를 여러 개 동시에 부르는 일이 생기면 그 부분만 async로 바꾸겠습니다.

### Q2-3. SQLite를 운영에 써도 되나요?
v1의 요구 조건이 "사내 PC 한 대, 외부 서비스 의존 금지, 비용 0"이었습니다. 사용자가 몇 명이고 쓰기가 드물어서 SQLite로 충분했고, WAL 모드로 쓰기 중에도 읽기를 막지 않게 했습니다.
v2는 관리형 PostgreSQL이 목표라서, 지금 SQLite로 개발하더라도 **전환 비용이 0이 되게** 규칙 여섯 개를 지킵니다: 소문자 테이블명, 정확한 타입, 원시 SQL 금지, 정렬 없는 페이지네이션 금지, 연결 설정은 `config.py`에서 분기, 스키마 변경은 Alembic.
→ **실제로 부딪힌 SQLite와 Postgres 차이는?**
- DECIMAL이 없어 float64 경유 → 유효자릿수 15 초과 시 반올림 (P-02)
- 외래키가 기본 꺼져 있음 → 연결마다 `PRAGMA foreign_keys=ON`
- `ALTER TABLE` 지원이 빈약 → Alembic batch 모드 (임시 테이블로 우회)
- 대소문자를 안 가려서 대문자 테이블명 문제가 SQLite에서는 안 보임 (P-06)

### Q2-4. 왜 React나 Vue를 안 썼나요?
화면이 7개 수준이고, 무거운 계산은 서버가 합니다. 빌드 도구 없이 파일을 열어 고칠 수 있어야 사내에서 유지보수가 됩니다(D7). 그래서 네이티브 ES Module로 갑니다.
대가는 상태 관리와 컴포넌트 재사용을 직접 해야 한다는 점이라, 공통 유틸을 `app.js` 한 곳에 모읍니다.
→ **언제 프레임워크로 갈 건가?** 화면 간에 공유하는 상태가 많아지거나, 폼이 복잡해지거나, 프론트 전담 인력이 생기면 다시 판단합니다.

### Q2-5. 왜 모놀리식인가요?
사용자 수, 팀 규모, DB 하나라는 조건에서 서비스를 쪼갤 이유가 없었습니다. 무엇보다 이 프로젝트의 핵심이 "두 시스템을 합쳐 동기화를 없앤 것"인데, 서비스를 나누면 그 동기화 문제를 다시 들여옵니다.

### Q2-6. Firebase Data Connect를 언급하던데, 왜 Firestore 같은 NoSQL이 아닌가요?
구 Sales Hub가 Firestore를 쓰다 REST로 옮긴 흔적이 있었고, 한때 Firestore 전환을 가정했습니다. 철회한 이유는 이 도메인이 **관계형**이기 때문입니다. 주차×품목×창고 GROUP BY, 외래키, 유니크 제약, 트랜잭션이 핵심입니다.
Data Connect는 관리형 PostgreSQL이라 코드가 일반 Postgres와 같고, 둘 중 무엇으로 할지는 배포 시점에 정하기로 했습니다(D13). Firestore를 전제로 넣었던 장치들(Port-Adapter 계층, 정수 최소 단위 금액, ULID 키)도 함께 걷어냈습니다.
→ **브라우저가 Firebase에 직접 붙으면 서버가 필요 없지 않나?** 그러면 계산 로직이 JS로 가고, "운영자는 재고는 바꾸되 기준 정보는 못 바꾼다" 같은 3단계 권한을 Security Rules로 표현해야 합니다. 규칙과 계산이 두 곳에 흩어집니다. 그래서 FastAPI를 앞에 둡니다(D3).

### Q2-7. 계산을 왜 서비스로 뺐고, 예측은 왜 순수 함수인가요?
v1은 재고 라우터 하나가 849줄이었고 계산이 다 그 안에 있었습니다. 테스트하려면 매번 HTTP를 거쳐야 했고, 같은 규칙이 화면마다 조금씩 다르게 구현됐습니다.
예측을 순수 함수로 두니 DB 없이 39개 테스트로 공식을 고정할 수 있었고, 발주 계획과 재고 현황이 같은 함수를 씁니다.

### Q2-8. 원시 SQL을 금지한 이유는? ORM은 느리지 않나요?
두 가지 이유입니다. 날짜 함수·문자열 연결이 방언마다 달라 이식성이 깨지고, 문자열 조립은 인젝션 위험이 있습니다.
집계는 여전히 SQL로 내려 보냅니다. SQLAlchemy 표현식으로 `GROUP BY`를 쓰는 것이라 ORM 객체를 만들지 않습니다(`derive.rebuild_weekly_metrics`).
→ **예외는?** 관리자 진단 엔드포인트의 `text("SELECT 1")` 하나가 규칙에 걸립니다. 알려진 경미한 항목으로 기록해 뒀습니다.

## 3. 데이터 모델링

### Q3-1. 테이블 구성을 설명해 주세요.
14개를 다섯 묶음으로 나눕니다.
- 기준 정보: `brand`, `product`, `product_alias`, `warehouse`, `channel`, `warehouse_product_moq`, `logistics_cost`
- 공급망: `inbound`, `inventory_snapshot`, `monthly_order_plan`
- 판매: `sales_order`, `promotion`
- 파생: `weekly_metric`
- 인증: `user_account`

SCM과 판매를 잇는 접합점은 두 개뿐입니다. `product_alias`(판매 데이터의 제품명 → 품목)와 `channel.warehouse_id`(판매 채널 → 재고를 소진시키는 창고). 이 둘만 연결되면 나머지는 서로를 몰라도 됩니다.

### Q3-2. 판매 원장에 원본 제품명·채널명을 그대로 두는 건 정규화 위반 아닌가요?
같은 사실을 두 번 저장하는 게 아니라 **서로 다른 두 사실**입니다. 원본 문자열은 "채널이 이렇게 보고했다"는 사실이고, `product_id`는 "우리가 그걸 이 품목으로 해석했다"는 해석입니다. 해석은 바뀔 수 있습니다.
덕분에 별칭을 나중에 추가해도 재업로드 없이 다시 해석되고(`/api/sales/resolve`), 미매핑 건이 집계에서 조용히 사라지지 않고 목록으로 드러납니다.
→ **매핑을 왜 추측하지 않나?** 구 Sales Hub는 채널명 접두어로 그룹을 추측했습니다. 추측한 집계는 틀려도 드러나지 않습니다. 모르면 '기타'로 모으고 미매핑 목록에 띄웁니다.

### Q3-3. 금액 컬럼이 왜 `Numeric(15,2)`인가요? 보통 18이나 19를 쓰지 않나요?
실측 때문입니다. `Numeric(18,2)`에 `999999999999999.99`를 넣었더니 `1000000000000000.00`으로 저장됐습니다. SQLite에는 DECIMAL이 없어 SQLAlchemy가 float64를 경유하고, float64는 유효자릿수 15까지만 정확합니다.
Postgres는 임의 정밀도라 이 제약이 없지만, 같은 코드가 양쪽에서 똑같이 동작해야 하므로 낮은 쪽에 맞췄습니다. 상한은 약 10조 원이라 업무상 손해가 없습니다.
정밀도 숫자를 컬럼마다 쓰지 않고 `types.py`의 `Money`/`UnitPrice`/`Rate`/`Percent`만 쓰게 했고, 한계값 왕복을 테스트로 고정했습니다.
→ **정수 최소 단위(원·센트)로 저장하면 되지 않나?** Firestore를 전제로 할 때 검토했다가 Postgres로 정해지며 철회했습니다. 외화 단가는 소수점 4자리가 필요해서 `Numeric`이 더 자연스럽습니다.
→ **입력 단계에서는?** openpyxl이 숫자 셀을 float으로 주므로 `Decimal(str(value))`로 바꿉니다. `Decimal(0.1)`은 `0.1000000000000000055…`입니다.

### Q3-4. enum을 왜 DB 네이티브 ENUM이 아니라 문자열 + CHECK로 했나요?
Postgres 네이티브 ENUM은 값을 추가할 때 `ALTER TYPE`이 필요해 마이그레이션이 까다롭고, SQLite에는 대응 개념이 없습니다. 문자열 + CHECK는 양쪽에서 똑같이 동작합니다.
CHECK의 값 목록은 손으로 쓰지 않고 Python enum에서 생성합니다(`check_in`). 두 곳에서 관리하면 언젠가 어긋나고, 어긋난 사실은 잘못된 값이 저장된 뒤에야 드러납니다.
→ **`EnumStr`은 왜 만들었나?** `String` 컬럼에 `Mapped[SomeEnum]` 힌트를 달아도 SQLAlchemy는 강제하지 않아서, DB에서 다시 읽으면 그냥 `str`이 나옵니다. 그 상태로 `category.expiry_label`을 부르면 `AttributeError`가 납니다. **같은 세션에서 방금 만든 객체는 진짜 enum이라 테스트는 통과하고, DB에서 다시 읽는 실제 경로에서만 터집니다.** 그래서 저장·조회 시 변환을 타입이 책임지게 했습니다.

### Q3-5. ISO 주차를 왜 컬럼으로 저장하나요? 날짜에서 계산하면 되잖아요.
세 가지 이유입니다. 주차 조회가 인덱스를 탑니다. `strftime`(SQLite)과 `EXTRACT`(Postgres)의 방언 차이를 피합니다. 연말 경계를 한 곳에서 처리합니다 — 2025-12-29(월)은 달력상 2025년이지만 ISO로는 2026년 1주차입니다. 직접 구현하면 12월 마지막 주 실적이 엉뚱한 해로 갑니다. 그래서 표준 라이브러리 `isocalendar()`를 쓰고 테스트로 고정했습니다.
→ **출고일이 바뀌면 주차가 어긋나지 않나?** 판매 건은 등록과 삭제만 있고 수정 API가 없습니다. 주차는 등록 시점에 출고일에서 한 번 계산합니다.

### Q3-6. 발주(order)와 발주 계획(plan)을 한 테이블로 합친 이유는?
v1은 `ORDER_DB`와 `MONTHLY_ORDER_PLAN`이 같은 사실을 두 곳에 저장해서 어느 쪽이 진실인지 알 수 없었습니다. 이 회사는 발주가 월 1회라 **확정된 계획이 곧 주문**입니다. `status=CONFIRMED`이면 나간 주문이고 `purchase_code`(발주번호)로 입고와 이어집니다. 실제 발주 수량은 실무자 수정값(`user_modified_qty`)입니다.
→ **한 달에 같은 품목을 쪼개서 주문하게 되면?** 그때 별도 테이블을 되살립니다. 쓰이지 않는 테이블을 미리 들고 가면 반쯤 구현된 채로 남아 진실이 흐려집니다.

### Q3-7. 재고를 왜 입출고 이벤트가 아니라 스냅샷으로 관리하나요?
이 시스템은 창고관리시스템(WMS)이 아닙니다. 재고 수량의 진실은 창고(3PL)가 주 단위로 보내는 재고 보고서에 있고, 우리는 그걸 시점별 스냅샷으로 받습니다. 주간 출고량은 스냅샷 차이(`기초 + 입고 - 기말`)로 파생합니다.
대가는 해상도입니다. 주중 변화는 볼 수 없습니다. 발주가 월 단위, 판단이 주 단위라 업무상 충분합니다.
→ **스냅샷 유니크 키에 유통기한이 들어가는데, 유통기한이 NULL이면?** 좋은 지적입니다. SQL의 UNIQUE는 NULL끼리 서로 다르다고 봐서 DB 제약이 중복을 막지 못합니다. 그래서 등록·업로드 경로에서 `(일자, 창고, 품목, 기한)`으로 먼저 조회해 있으면 수량을 갱신합니다(SQLAlchemy가 `== None`을 `IS NULL`로 바꿉니다). DB 차원에서 막으려면 Postgres 15의 `NULLS NOT DISTINCT`나 부분 유니크 인덱스를 쓰겠습니다.

### Q3-8. 삭제 대신 비활성화를 쓰는 이유는?
사용자를 지우면 "누가 등록했는가"가 사라지고, 같은 아이디가 재사용되면 과거 기록의 주체가 바뀝니다. 품목·창고는 다른 테이블이 외래키로 참조하고 있어 지우면 과거 실적이 깨집니다.

### Q3-9. 제약조건 이름 규칙은 왜 강제하나요?
이름 없는 제약은 Alembic이 `downgrade()`에서 지목할 수 없고, SQLite의 batch ALTER도 실패합니다. DB가 자동 생성한 이름은 방언마다 달라 마이그레이션이 이식되지 않습니다. `MetaData(naming_convention=…)`로 모든 제약에 이름을 붙이고, 이름 없는 제약이 있으면 실패하는 테스트를 뒀습니다.

### Q3-10. 시간대는 어떻게 다루나요?
저장은 UTC(`DateTime(timezone=True)`, `datetime.now(UTC)`)이고 표시는 `Asia/Seoul`입니다. SQLite는 timestamptz가 없어 naive로 저장되지만 애플리케이션이 항상 UTC로 다루므로 Postgres로 옮겨도 값이 그대로 유효합니다. 업무 날짜(출고일·유통기한)는 시각이 없는 `Date`입니다.

### Q3-11. 인덱스는 어떤 기준으로 걸었나요?
실제 질의 패턴 기준입니다.
- `weekly_metric(product_id, iso_year, iso_week)` — 예측이 품목별 최근 12주를 시간순으로 읽음
- `sales_order(iso_year, iso_week)`, `(brand_id, iso_year, iso_week)`, `ship_date` — 주차 재집계와 대시보드
- `sales_order(source_product_name)` — 미매핑 건 찾기
- `inbound(status)`, `(eta)`, `(expiry_date)` — 입고 예정과 유통기한 조회
- `inventory_snapshot(snapshot_date, product_id)` — 기준일 이전 최근 스냅샷

## 4. 수요 예측과 발주

### Q4-1. 예측 모델을 설명해 주세요.
```
평탄화 상수 S = 최근 12주 출고량 평균
감모 버퍼   L = 최근 12주 (출고량 - 판매량) 평균
주간 수요   D = S × 가중치 + L
기말재고(W) = 기말재고(W-1) + 입고예정(W) - D,   W = 1…24
제안 수량   = ⌈(D × 6 - 기말재고(24)) / 카툰 입수량⌉ × 카툰 입수량
```
예시를 들면: 출고 평균 100, 판매 평균 95면 감모 5, 주간 수요 105. 현재고 1,500, 10주 차 입고 1,200이면 재고일수는 14.3주로 **과잉**인데도,
24주 뒤 재고가 180이라 안전재고 630에 못 미쳐 456개(24×19)를 제안합니다. 지금 주문하면 6개월 뒤에 도착하기 때문입니다.

### Q4-2. 왜 머신러닝을 안 썼나요?
발주는 돈이 나가는 결정이고, 담당자가 "왜 이 숫자냐"에 답할 수 있어야 합니다. 그래서 API가 결과만이 아니라 평탄화 상수·감모 버퍼·주간 수요를 함께 돌려주고, 화면에서 손으로 다시 계산할 수 있게 합니다.
데이터도 품목별 주 단위라 표본이 작아서 복잡한 모델이 이길 여지가 크지 않습니다. 사람의 판단(행사, 성수기)은 **가중치**로 넣습니다.
→ **그럼 정확도는 어떻게 검증했나?** 솔직히 아직 백테스트를 하지 않았습니다. 한다면 과거 시점 t까지의 데이터로 t+1~t+k주를 예측해 실제와 비교하는 롤링 방식으로, 품목별 MAE와 **편향**(늘 과대/과소인가)을 보고, "직전 주 그대로" 같은 단순 기준보다 나은지 확인하겠습니다. 발주에서는 평균 오차보다 편향이 더 비쌉니다.
→ **추세나 계절성은 반영 못 하지 않나?** 맞습니다. 단순 평균은 추세를 늦게 따라가고 계절성을 모릅니다. 지금은 가중치로 보정합니다. 사칙연산 원칙 안에서 다음 단계를 고른다면 가중 이동평균, 홀트 선형 평활(수준+추세, 여전히 손으로 따라갈 수 있음), 작년 같은 주차로 만든 계절 지수 순으로 검토하겠습니다. 설명 가능성이 요구사항이라 사용자와 먼저 합의합니다.

### Q4-3. 왜 12주, 왜 단순 평균인가요?
12주는 약 3개월로 적정 재고 기준(13주)과 같은 시간 척도이고, 한두 주의 스파이크를 충분히 눌러 줍니다. 단순 평균은 설명이 가장 쉽습니다.
데이터가 12주보다 적으면 **있는 만큼만** 평균냅니다. 빈 주를 0으로 채우면 신규 품목의 수요를 실제보다 낮게 잡습니다.
→ **판매가 없던 주(진짜 0)와 데이터가 없는 주를 어떻게 구분하나?** 지금은 구분하지 못합니다. 집계 행은 판매가 있던 (주차, 품목, 창고)에만 생기고, 행이 없는 주는 건너뜁니다. 그래서 띄엄띄엄 팔리는 품목은 판매가 있던 주만으로 평균이 나와 수요가 **과대평가**됩니다. 코드는 "데이터 없는 주를 0으로 잡으면 과소평가한다"는 쪽을 막는 선택을 했고, 그 대가가 이것입니다. 재고 스냅샷이 있는 주는 판매 0을 명시적인 0행으로 기록하는 식으로 둘을 구분해야 합니다.

### Q4-4. 감모 버퍼는 뭐고, 왜 가중치를 안 곱하나요?
실제로 재고에서 빠진 양(출고)과 팔린 양(판매)의 차이입니다. 파손, 분실, 기록 안 된 이관이 여기 잡힙니다.
가중치는 "행사라서 1.5배 팔릴 것"처럼 **판매**에 대한 판단입니다. 파손은 판매량과 무관하게 일정하게 생긴다고 봐서 곱하지 않습니다. 곱하면 행사 때 파손도 1.5배가 됩니다.
→ **음수가 될 수 있나?** 판매가 출고보다 많으면(반품, 집계 시차) 음수가 됩니다. 그대로 둡니다. 테스트로 그 경우를 고정했습니다.

### Q4-5. 제안 수량을 왜 24주 끝 시점 재고로 계산하나요?
업무 규칙이 "리드타임 때문에 6개월 뒤 도착분을 주문한다"입니다. 이번 달 주문은 시뮬레이션 끝쯤 도착하니, **도착 시점에 안전재고 6주분이 남도록** 부족분을 채웁니다. 그래서 화면에 발주월과 도착월을 같이 보여줍니다.
→ **6개월이면 26주인데 왜 24주?** 업무에서 "약 24주"로 써 온 관례를 따랐습니다. 차이가 있다는 건 알고 있고, 품목마다 리드타임이 다르면 품목 속성으로 빼는 게 맞습니다.
→ **시뮬레이션 중간에 재고가 음수가 되면?** 음수를 허용해서 누적 부족분이 제안 수량에 더해집니다. 이건 "못 판 수요가 이월된다(백오더)"는 가정입니다. 실제로 판매 기회가 사라지는 업종이면 과다 발주가 됩니다. 그리고 6개월 뒤 도착하는 주문은 그 전의 품절을 막지 못하므로, 그건 항공 전환 경보가 맡습니다.

### Q4-6. 항공 전환 경보는 어떻게 동작하나요?
12주 차 예상 재고가 음수면 "N개 부족, 항공이면 약 2주에 긴급 입고 가능"을 띄웁니다.
→ **한계는?** 12주 **한 시점**만 봅니다. 6주 차에 품절됐다가 10주 차 입고로 회복되면 경보가 안 뜹니다. `first_stockout_week`가 12 이하이면 띄우도록 바꾸는 게 맞습니다. 값은 이미 계산되고 있어 수정이 작습니다.

### Q4-7. 안전재고 6주는 어디서 나왔나요? 통계적 안전재고(z·σ·√LT)는 왜 안 썼나요?
히트맵의 "위험" 경계가 6주라서 같은 기준을 썼습니다. 화면과 발주 기준이 어긋나지 않게 하려는 겁니다.
표준편차 기반 안전재고는 수요 변동이 큰 품목에 더 정확하지만 실무자에게 설명하기 어렵습니다. 도입한다면 변동계수가 큰 품목에만 적용하고 "평소보다 들쭉날쭉해서 +N주"처럼 풀어서 보여주겠습니다.

### Q4-8. 수요가 0이면 재고일수는?
0으로 나누면 예외 대신 무한대를 돌려주고 '과잉'으로 분류합니다. 화면은 '소진 불가'로 표시합니다. JSON은 `Infinity`를 표현하지 못하므로 응답 직전에 `None`으로 바꿉니다(`nullable_weeks`).

### Q4-9. "실시간 시뮬레이션"은 어떻게 구현했나요?
v1은 수량 입력과 가중치 슬라이더의 `input` 이벤트마다 클라이언트에서 다시 계산하고 히트맵 색을 바꿉니다. "시뮬레이션 실행" 버튼을 일부러 없앴습니다. 서버 부하도 없는 단순 계산인데 버튼을 매번 눌러야 하는 게 문제로 개선 이력(`docs/history.md` 7.3)에 남아 있고, 그 뒤로 규칙이 됐습니다.
v2는 시뮬레이션 API가 저장 없이 조회 시점에 계산하고(`/api/order-plan/simulation?weight_factor=`), 저장은 별도 요청으로 합니다.

### Q4-10. 확정된 발주 계획을 재시뮬레이션하면?
건드리지 않습니다. 이미 발주번호가 붙어 나간 주문이라 수량이 바뀌면 발주와 기록이 어긋납니다. 수정·삭제 API도 확정 건은 409로 거부합니다.

## 5. 재고 · 유통기한 · 이관

### Q5-1. 재고일수는 어떤 재고로 계산하나요?
(품목, 창고)마다 **기준일 이전 가장 최근 스냅샷**입니다. 이 규칙은 `stock_on()` 한 함수에만 있고 재고 현황·유통기한·이관·발주가 다 이걸 씁니다. 두 벌이 되면 화면마다 다른 재고가 보이기 때문입니다.
→ **창고마다 스냅샷 날짜가 다르면?** 각자의 최근 스냅샷을 쓰고, 어느 날짜 스냅샷인지도 같이 돌려줍니다. 오래된 스냅샷이면 화면에서 경고할 수 있게 하려는 겁니다.

### Q5-2. FEFO 위험 판정을 설명해 주세요.
기한이 이른 로트부터 나간다고 보면, 뒤 로트는 앞 로트가 다 빠져야 소진이 시작됩니다. 그래서 **앞에 쌓인 물량까지 합쳐** 소진 주수를 계산합니다.
예: 주간 수요 50. 로트 A(30일 남음, 200개)는 4주 = 28일이라 안전. 로트 B(60일 남음, 300개)는 (200+300)/50 = 10주 = 70일이라 위험. B만 보면 6주면 다 나가지만 A가 먼저 나가야 합니다.
→ **기한이 없거나 판매 이력이 없으면?** "위험 없음"이 아니라 "판단 불가"로 따로 표시합니다(`is_judgeable`). 판매 채널이 없는 HUB를 위험으로 칠하면 화면이 전부 빨개져서 진짜 위험이 묻힙니다.
→ **HUB 재고는 결국 판단을 못 하는 것 아닌가?** 맞습니다. HUB는 이관으로 빠지는데 이관이 아직 주차 집계에 들어가지 않습니다(`transfer_qty` 컬럼만 있음). 이관 실적을 집계에 넣으면 HUB도 판단할 수 있게 됩니다.

### Q5-3. 이관 제안 알고리즘은?
1. 모든 (품목, 창고)의 재고일수를 계산해 **낮은 순**으로 정렬
2. 거점별 부족분 = 주간수요 × 9주 - 현재고
3. MOQ 배수로 올림 (창고·품목 예외 → 창고 기본값)
4. HUB 잔여 재고를 넘지 않게 깎고, 깎였으면 `shortfalls`에 기록
5. 구간 물류비 × 카툰 수로 비용 표시

→ **왜 9주인가?** 적정(13주)까지 채우면 여유 있는 거점까지 흔듭니다. 9주는 '주의'와 '양호'의 경계라, 주의 구간을 벗어나는 데까지만 채웁니다.
→ **왜 최적화(선형계획법)가 아니라 탐욕적 방식인가?** 업무 규칙이 "급한 곳부터"이고 품목·창고 수가 작습니다. 최적화로 물류비를 최소화할 수는 있지만 왜 그렇게 배분했는지 설명하기 어렵습니다. 비용은 판단 참고용으로 같이 보여줍니다.
→ **HUB 재고가 모자라면 공정한가?** 재고일수가 가장 낮은 곳부터 줍니다. 못 채운 곳은 목록으로 드러냅니다.

### Q5-4. 재고 자산 평가는 어떻게 하나요?
원칙은 마스터의 예상 단가가 아니라 **입고 때 실제로 결제한 원화 금액**을 역추적하는 겁니다. 환율과 운임이 실제 원가를 바꾸기 때문입니다.
v1은 재고 로트를 (품목, 유통기한)으로 입고 건과 맞춰 `결제 원화 ÷ 수량`을 단가로 썼습니다.
→ **한계는?** v1은 입고 건을 못 찾으면 `매입가 × 1350`으로 대체했는데, 환율이 코드에 박혀 있었습니다. v2에는 아직 이 기능을 옮기지 않았고 컬럼(`payment_amount_krw`)만 준비돼 있습니다. 옮길 때는 발주번호(`purchase_code`)로 입고와 로트를 잇고, 원가 계층을 선입선출로 쌓거나 이동평균을 쓰고, 대체 환율은 설정이나 환율 테이블에서 가져오겠습니다.

## 6. 파생 집계와 데이터 정합성

### Q6-1. "동기화 대신 파생"이 무슨 뜻인가요?
두 시스템을 합칠 때 처음 떠오른 건 양방향 동기화였습니다. 동기화는 지연, 충돌, 어느 쪽이 진실인지의 문제를 늘 데려옵니다. 같은 DB로 합치면 동기화할 것이 없습니다.
판매 원장(`sales_order`)이 진실이고, 주차 집계(`weekly_metric`)는 그걸 읽기 쉽게 정리한 사본입니다. 언제든 원장에서 다시 만들 수 있습니다.

### Q6-2. 왜 DB 뷰가 아니라 실제 테이블인가요?
예측이 품목마다 12주치를 반복해 읽는데 매번 원장을 스캔하면 느립니다. 머티리얼라이즈드 뷰는 SQLite에 없어 이식성을 잃습니다. 그리고 엑셀로 직접 올린 집계값(`IMPORTED`)은 원장에서 만들 수 없어서 어차피 저장할 곳이 필요합니다.
대가는 최신성입니다. 그래서 원장이 바뀌는 경로(업로드, 등록, 삭제, 매핑 해석)마다 해당 주차를 다시 계산합니다.

### Q6-3. 멱등성은 어떻게 보장하나요?
재계산이 "그 주차의 파생 행 삭제 → 원장에서 다시 합산 → 삽입"이라, 몇 번 돌려도 같은 결과입니다. `(주차, 품목, 창고)` 유니크 제약이 중복을 막고, 두 번 돌려 값이 같은지 테스트합니다.
엑셀로 올린 `IMPORTED` 행은 미리 키를 확보해 두고 삭제·재작성 대상에서 뺍니다.
→ **`synchronize_session="fetch"`는 왜?** `False`로 벌크 삭제하면 DB에서는 지워져도 세션에 객체가 남습니다. SQLite가 rowid를 재사용하면 새 행과 식별자가 겹쳐 낡은 객체를 읽습니다. 실제로 SAWarning으로 발견했습니다(P-15).

### Q6-4. 가장 기억에 남는 버그는? (P-14)
- **상황**: 예측 단위 테스트 141개가 전부 통과한 상태였습니다
- **발견**: 시드 데이터로 파이프라인을 끝까지 돌려보니 한 품목의 주간 수요가 **-44.9**였습니다
- **원인**: 출고량 = 기초 + 입고 - 기말인데, 스냅샷이 없는 주는 `0 + 0 - 0 = 0`이 되고, `0 >= 0`이라 판매량으로 대체하는 폴백도 안 걸려 0이 저장됐습니다. 평탄화 상수가 0, 감모 버퍼가 `0 - 판매량`으로 음수
- **왜 테스트가 못 잡았나**: 테스트마다 기초·기말 스냅샷을 둘 다 만들어 줘서 "데이터 없음" 경로를 한 번도 안 탔습니다
- **해결**: 조회 함수가 수량과 함께 **어느 스냅샷을 썼는지**를 돌려주게 하고, 스냅샷이 없거나 기초·기말이 같은 스냅샷이면 손대지 않게 했습니다. 결손 경로 테스트를 추가했고, 시드가 주 1회 스냅샷을 만들게 바꿨습니다
- **교훈**: "없는 데이터와 0인 데이터를 구분한다", 그리고 기능이 끝나면 실데이터로 전 구간을 돌려 숫자를 눈으로 본다

### Q6-5. 시드 데이터에서 겪은 다른 문제는? (P-17)
행사 ROI를 붙이고 시드로 돌렸더니 행사 4건 중 3건이 판매 0, 리프트 -100%였습니다. 예외도 경고도 없었고 테스트 55개도 통과했습니다.
행사 기간은 고정 오프셋으로, 판매는 임의 요일로 찍혀서 두 분포가 안 겹쳤던 겁니다. "데이터는 있는데 기능이 보는 구간에는 없는" 상태라 정상 경로(리프트 계산)를 한 번도 안 탔습니다. 그 와중에 **시작 전 행사가 -100%로 보이는 설계 결함**이 묻혀 있었습니다.
시드를 실제 판매 건에 붙여 만들도록 바꾸고, 예외 경로(시작 전 행사)는 이름으로 드러나게 하나만 남겼습니다. `-100%`가 세 줄 연속이면 그건 데이터가 아니라 시드의 모양입니다.

### Q6-6. 데이터 정합성이 깨질 수 있는 지점은 없나요?
있습니다. 코드를 다시 보면서 찾은 것들입니다.
1. **판매 삭제 후 집계가 남는다** — 삭제 후 재계산 대상을 "그 출고일에 남은 주문"에서 찾는데, 같은 날 다른 주문이 없으면 대상이 비어 집계 행이 그대로 남습니다. 2026-10-08에 직접 재현했습니다. 고치려면 삭제한 건의 **주차를 명시적으로 넘겨** 그 주차의 파생 행을 지우고 다시 만들어야 합니다
2. **재고 흐름 계산이 API 경로에 연결돼 있지 않다** — `apply_inventory_flow`를 시드만 부릅니다. API로만 데이터를 넣으면 출고량 = 판매량이라 감모 버퍼가 늘 0이고, 판매 재집계가 이미 채운 재고 흐름 값을 지웁니다. 재집계 뒤와 스냅샷 업로드 뒤에 해당 주차의 재고 흐름을 다시 적용해야 합니다
3. **등록과 재집계가 한 트랜잭션이 아니다** — 판매 등록을 커밋한 뒤 재집계를 따로 커밋합니다. 재집계가 실패하면 원장과 집계가 어긋납니다(11절)

검증 방법으로는 "처음부터 전체 재계산한 결과 == 증분 재계산을 거친 결과"라는 **불변식 테스트**를 넣겠습니다. 이 방식이면 1번 같은 문제가 바로 잡힙니다.

## 7. 매출 분석

### Q7-1. Sales Hub의 `analytics.js`를 Python으로 옮기면서 무엇을 바꿨나요?
계산 규칙은 그대로 옮기고 네 가지를 의도적으로 바꿨습니다.
1. **입력이 정규화된 원장** — 매핑이 DB에 있으니 채널 접두어로 그룹을 추측하던 로직을 없앴습니다
2. **출력에 HTML 금지** — 구 알림 문구에 `<strong>`이 박혀 있었습니다. 그 문자열을 `innerHTML`에 꽂으면 업로드된 제품명이 스크립트가 됩니다(D15)
3. **주간 비교를 같은 경과일수끼리** (D14)
4. **기준선 없음은 `None`** — 구 버전은 리프트를 `99999`, 시작 전 행사를 `-100%`로 내보냈습니다(D16)

포팅하지 않은 것도 있습니다. 클릭 시 나오는 드릴다운과 "왜 변했나" 문장은 계산이 아니라 문장 조립이라 화면 형태가 정해지는 Phase 5에서 만듭니다.

### Q7-2. "같은 경과일수끼리 비교"를 예로 설명해 주세요.
수요일에 대시보드를 열면 이번 주는 월~수 3일치입니다. 구 버전은 직전 주를 월~일 7일치 통째로 비교해서 WoW가 늘 -50% 안팎의 폭락으로 보였습니다. 지금은 직전 주도 월~수만 잘라 비교합니다. 월 비교는 원래 "지난달 같은 날까지"였는데 주 비교만 어긋나 있던 걸 맞춘 겁니다. 3/31의 전월은 2/28로 클램프합니다.

### Q7-3. 채널 점유율 변화를 왜 %p로 보여주나요?
점유율은 이미 비율이라 그 변화는 퍼센트 포인트입니다. 매출이 20% 늘어도 다른 채널이 더 늘면 점유율은 떨어집니다. 증감률과 섞으면 "늘었는데 줄었다" 같은 혼동이 생겨서 필드명부터 `share_wow_pp`로 구분했습니다.

### Q7-4. 행사 리프트는 어떻게 계산하고, 한계는?
`(행사 기간 일평균 판매 / 직전 14일 일평균 - 1) × 100`. 총량이 아니라 **일평균**인 이유는 행사 기간과 기준선 길이가 달라서입니다. 진행 중인 행사는 기준일까지 지난 일수로 나눕니다. 전체 기간으로 나누면 일평균이 낮게 나옵니다.
→ **한계는?** 인과가 아니라 지표입니다. 직전 14일에 다른 행사가 있었거나 계절 변화가 있으면 기준선이 오염되고, 대조군이 없습니다. 화면에서 "행사 리프트 가능성"처럼 단정하지 않는 표현을 쓰는 이유입니다.

### Q7-5. 알림 임계값은 어떻게 정했나요?
구 Sales Hub 설정(`ANALYTICS_THRESHOLDS`)을 그대로 옮겼습니다. 라인업 +50% / -25%, 채널 -20%, 채널 상승은 행사가 걸려 있으면 +30%, 없으면 +50%부터. 직전 주가 0인 대상은 늘 +100%라 제외하고, 변화가 큰 순으로 5개까지만 보여줍니다. 다섯 개를 넘기면 아무도 읽지 않습니다.
→ **임계값을 데이터로 정할 수는 없나?** 품목별 과거 변동폭(표준편차)으로 "평소보다 2배 이상 흔들림"처럼 정하는 게 더 낫습니다. 다만 포팅 단계에서 숫자까지 바꾸면 구 버전과 결과를 비교해 검증할 수 없어서 그대로 옮겼습니다.

### Q7-6. 대시보드가 원장 전체를 메모리로 읽던데, 커지면요?
지금은 원장을 한 번 읽고 KPI·믹스·포트폴리오·알림·추이를 메모리에서 계산합니다. 같은 데이터를 예닐곱 번 훑기 때문에 구간마다 쿼리를 던지는 것보다 단순하고 빠릅니다. 데이터가 작을 때 맞는 선택입니다.
커지면 두 단계로 바꾸겠습니다. 먼저 **필요한 기간만 읽습니다.** 대시보드가 보는 가장 긴 구간(추이 12개월 또는 전월)으로 `ship_date` 범위를 걸면 됩니다. 그다음 합계를 SQL `GROUP BY`로 내립니다. 원장에는 이미 `(brand_id, iso_year, iso_week)`와 `ship_date` 인덱스가 있습니다.

## 8. 엑셀 업로드

### Q8-1. 왜 API 연동이 아니라 엑셀 업로드인가요?
채널과 창고가 엑셀로 데이터를 주고, 실무자가 이미 엑셀로 일합니다. 업무 흐름을 바꾸지 않는 쪽을 택했습니다. 대신 양식을 시스템이 만들어 주고(헤더 + 회색 예시 행), 열은 위치가 아니라 **헤더 이름**으로 찾습니다.
WMS나 판매 채널 API 연동은 그다음 단계입니다. 원장 구조가 정해져 있으니 입력 경로만 늘리면 됩니다.

### Q8-2. 업로드 중 일부 행이 틀리면 어떻게 하나요?
행 단위로 실패합니다. 틀린 줄은 "몇 번째 줄, 어느 칸, 왜"를 모아 돌려주고 나머지는 적재합니다. 구 코드는 `except Exception: continue`로 조용히 버렸습니다.
→ **그럼 원자성이 깨지지 않나? 고친 파일을 다시 올리면?** 정확한 지적입니다. 재고 스냅샷은 자연키로 갱신이라 다시 올려도 안전하지만, **판매 원장은 추가만 해서 파일 전체를 다시 올리면 정상 행이 중복됩니다.** 해결책은 세 가지 중 하나입니다.
1. 업로드 단위 식별자 + 행 해시로 같은 행을 막는 멱등 키
2. 주문번호가 있는 채널은 `(brand, order_no, product, ship_date)` 유니크
3. "이 기간을 교체" 모드 — 해당 브랜드·기간 판매를 지우고 새로 넣기

실무 흐름(채널별 주간 파일)을 보면 3번이 가장 단순하고 사용자에게도 설명하기 쉽습니다.
→ **아예 전체 롤백 모드는?** "검증만 하기"(dry-run)로 오류를 먼저 보여주고, 오류가 0일 때만 적재하는 선택지를 주는 게 좋습니다.

### Q8-3. 엑셀 날짜 처리에서 어려웠던 점은?
날짜가 다섯 가지 형태로 들어옵니다. `datetime` 객체, 서식이 '일반'인 칸의 **일련번호**(기준일 1899-12-30, 1900년 윤년 버그 때문), `2026년 6월 19일`, `26-06-19`, `2026-06-19 00:00:00`.
구 코드는 시간을 떼려고 공백으로 잘랐는데(`split(" ")[0]`), 그러면 `2026년 6월 19일`이 `2026년`이 됩니다. 지금은 `:`가 있을 때만 시간을 뗍니다. 일련번호는 20000~100000(약 1954~2173년) 범위일 때만 날짜로 봅니다.

### Q8-4. pandas를 왜 걷어냈나요?
행 단위로 읽는 데 DataFrame이 필요 없습니다. 더 큰 이유는 pandas가 빈 칸을 `NaN`(float)으로 만든다는 점입니다. 그래서 구 코드는 셀마다 `pd.notna()`와 `str()`을 둘렀고, 그 과정에서 날짜와 금액이 문자열로 뭉개졌습니다. openpyxl은 셀 타입을 그대로 줍니다. 의존성도 가벼워집니다(D17).

### Q8-5. 대용량 파일은요?
openpyxl `read_only` 모드로 파일을 통째로 메모리에 올리지 않고, 500행마다 flush합니다. 업로드는 20MB로 제한합니다(한도 + 1바이트만 읽어 초과 판정).
수십만 행이 되면 요청 안에서 처리하지 않고 백그라운드 작업으로 넘기겠습니다. 다만 인프로세스 스케줄러는 쓰지 않기로 했으니(D4) Cloud Tasks 같은 외부 큐나 별도 워커로 갑니다.
→ **보안상 엑셀 파일 자체의 위험은?** `data_only=True`라 수식을 실행하지 않고 계산된 값만 읽습니다. 다만 xlsx는 zip 안의 XML이라 압축 폭탄이나 XML 공격 여지가 있습니다. openpyxl은 `defusedxml`이 설치돼 있으면 그걸 쓰는데 지금 의존성에 없습니다. 추가 대상입니다.

## 9. 보안

### Q9-1. 인증 방식을 설명해 주세요.
로그인하면 쿠키 두 개를 줍니다. `eibe_session`은 JWT가 든 **httpOnly** 쿠키라 JS가 읽을 수 없습니다. `eibe_csrf`는 JS가 읽을 수 있는 CSRF 토큰입니다. 상태를 바꾸는 요청은 CSRF 토큰을 `X-CSRF-Token` 헤더에 실어야 하고, 미들웨어가 쿠키 값과 헤더 값을 타이밍 공격에 안전하게 비교합니다(`secrets.compare_digest`).
보호 라우트는 JWT를 검증한 뒤 **매 요청 DB에서 사용자를 다시 읽어** 활성 여부를 확인하고 권한 등급을 비교합니다.

### Q9-2. 왜 localStorage 대신 쿠키인가요?
v1은 토큰을 localStorage에 뒀습니다. XSS 한 번이면 토큰이 밖으로 나갑니다. httpOnly 쿠키는 스크립트가 읽을 수 없습니다(D9).
대가는 CSRF입니다. 쿠키는 브라우저가 자동으로 보내니까요. 그래서 이중 제출 토큰과 `SameSite=Lax`를 같이 씁니다.
→ **이중 제출 쿠키가 왜 CSRF를 막나?** 다른 출처의 페이지는 우리 쿠키를 읽을 수 없어 헤더에 같은 값을 넣을 수 없습니다.
→ **약점은?** 공격자가 형제 서브도메인을 장악해 CSRF 쿠키를 덮어쓰면 뚫립니다. 보완하려면 CSRF 토큰을 세션에 묶어 서명(HMAC)하거나, `__Host-` 접두어 쿠키로 서브도메인 주입을 막겠습니다.
→ **로그인은 왜 CSRF 면제인가?** 세션 쿠키가 없을 때 호출되기 때문입니다. 그래서 로그인 CSRF(피해자를 공격자 계정으로 로그인시키기) 위험이 남습니다. `SameSite`는 쿠키를 **보내는** 것을 제한할 뿐이라 이걸 막지 못합니다. 로그인 요청의 `Origin`/`Referer` 헤더를 확인하거나, 로그인 전 세션에 CSRF 토큰을 발급하는 방식으로 보완하겠습니다.

### Q9-3. JWT인데 로그아웃하면 토큰이 무효화되나요?
**아니요.** 로그아웃은 쿠키를 지울 뿐이고, 탈취된 토큰은 만료(12시간)까지 유효합니다. 비활성화된 계정은 매 요청 DB 조회로 바로 막히지만 "이 토큰만 끊기"는 못 합니다.
보완책은 사용자 테이블에 `token_version`을 두고 JWT에 넣어, 로그아웃·비밀번호 변경 때 올리는 방식입니다. 어차피 매 요청 사용자를 조회하니 추가 비용이 없습니다.
→ **매 요청 DB를 조회할 거면 JWT를 왜 쓰나? 서버 세션과 뭐가 다른가?** 지금 구조에서는 큰 차이가 없다는 게 솔직한 답입니다. 세션 저장소를 따로 두지 않아도 되는 것과, 다중 인스턴스로 갈 때 공유 저장소 없이 서명만 검증하면 되는 여지를 남긴 정도입니다. 권한 변경을 즉시 반영하는 게 더 중요해서 DB 조회를 택했습니다.

### Q9-4. 비밀번호는 어떻게 저장하나요?
bcrypt입니다. 두 가지를 더 했습니다.
- **72바이트 문제**: bcrypt는 72바이트를 넘는 입력을 자르거나 거부합니다. 넘으면 SHA-256 hex(64바이트 ASCII)로 먼저 줄여 전체가 반영되게 했습니다. 원시 바이트 다이제스트가 아니라 hex를 쓰는 건, 바이트에 NUL이 섞이면 bcrypt 구현에 따라 거기서 잘리거나 거부되기 때문입니다
- **타이밍 공격**: 없는 계정이면 해싱을 건너뛰게 되는데, bcrypt가 일부러 느려서 응답 시간 차이로 계정 존재 여부가 드러납니다. 없는 계정에도 더미 해시로 같은 비용을 치르고, 오류 메시지도 구분하지 않습니다(P-13)

### Q9-5. 권한은 어떻게 설계했나요?
`VIEWER(0) < OPERATOR(1) < ADMIN(2)` 순위로 비교합니다. 조회는 로그인만, 재고·입고·판매 같은 업무 데이터 변경은 운영자, 기준 정보와 사용자는 관리자입니다. 구 SCM의 ADMIN/OPERATOR와 Sales Hub의 admin/viewer를 합친 겁니다.
핵심은 **인증이 기본값**이라는 점입니다. v1은 라우트마다 가드를 붙였고, 그 결과 `GET /api/users`가 무인증으로 전체 계정을 노출하고 있었습니다. 지금은 라우터에 가드를 걸어 소속 라우트 전체에 적용하고, 공개가 필요한 헬스체크만 별도 `public_router`에 둡니다.
→ **라우트에 `dependencies=[]`를 주면 안 되나?** FastAPI는 라우터와 라우트 의존성을 **합칩니다.** 빈 리스트로는 해제되지 않습니다. 직접 겪었습니다(P-01).
→ **엑셀 업로드는 종류마다 권한이 다르던데?** 종류가 경로 변수라 라우터 의존성으로는 나눌 수 없습니다. 기본은 운영자로 걸고, 기준 정보 종류만 핸들러 안에서 관리자를 추가로 확인합니다.

### Q9-6. 관리자 계정 관련 안전장치는?
- 서버 기동 시 `admin/admin` 자동 생성을 없앴습니다. 환경변수로 비밀번호를 명시할 때만 만들고, production에서는 흔한 비밀번호나 10자 미만을 거부합니다
- **마지막 관리자**는 권한을 내리거나 비활성화할 수 없습니다. 아무도 못 들어가는 시스템이 되면 DB를 직접 고쳐야 합니다
- 자기 계정은 비활성화할 수 없습니다

### Q9-7. 운영 환경 설정 실수는 어떻게 막나요?
`ENV=production`이면 설정 객체를 만들 때 검증해서, 하나라도 어기면 **기동 자체를 거부**합니다. 시크릿 32자 이상, HTTPS 전용 쿠키(`COOKIE_SECURE`), `DEBUG=false`, 부트스트랩 비밀번호 강도. 그리고 production에서는 Swagger 문서를 끄고, 처리 안 된 예외는 메시지 없이 "서버 오류"만 돌려줍니다. 개발용 시드 스크립트는 production에서 실행을 거부합니다.
로컬에서 시크릿을 비워 두면 임시 키를 만듭니다. 재시작하면 세션이 끊기지만 시크릿이 저장소로 새어 나갈 일이 없습니다.

### Q9-8. XSS와 SQL 인젝션은?
- XSS: 세션 토큰이 httpOnly라 읽히지 않고, 서비스는 HTML을 만들지 않고 데이터만 돌려줍니다. 화면은 `textContent`로 넣어야 합니다. CSP 헤더는 아직 없어서 추가 대상입니다
- SQL 인젝션: SQLAlchemy 표현식만 써서 값이 항상 바인딩됩니다. CHECK 제약 문자열을 f-string으로 만드는 곳이 있지만 값이 코드의 enum 상수라 사용자 입력이 들어가지 않습니다

### Q9-9. 무차별 대입(brute force)은요?
로그인 시도 제한은 아직 없습니다. bcrypt 비용이 속도를 늦추는 정도입니다. 계정·IP별 시도 횟수 제한과 일시 잠금을 넣겠습니다. 계정 잠금은 반대로 서비스 거부에 악용될 수 있어서 지연을 점점 늘리는 방식이 더 낫다고 봅니다.

## 10. 성능과 확장성

### Q10-1. 지금 구조에서 병목이 될 곳은?
알고 있는 곳은 네 군데입니다.
1. 매출 대시보드가 원장 전체를 메모리로 읽음 → 기간 한정 + SQL 집계 (Q7-6)
2. 재고 현황이 (품목, 창고)마다 이력 쿼리를 따로 던짐(N+1) → 품목·창고·주차 `GROUP BY` 한 번으로 전체 이력을 가져와 메모리에서 나누기
3. 유통기한 보고서가 스냅샷 전체를 읽고 파이썬에서 최신 날짜만 거름 → 최신 날짜 조건을 SQL로 내리기
4. 매핑 재해석(`resolve`)이 원장 행을 하나씩 순회 → `UPDATE … FROM` 형태의 벌크 갱신

지금 데이터 규모(품목 수십~수백, 창고 몇 개)에서는 문제가 아니라서 정확성과 가독성을 먼저 택했습니다.

### Q10-2. 사용자가 늘면 SQLite는?
WAL 모드라 읽기는 동시에 되고 쓰기는 한 번에 하나입니다. 사용자 수십 명, 쓰기가 업로드 중심이면 버팁니다. 그 이상은 계획대로 PostgreSQL로 갑니다. `.env`의 연결 문자열 한 줄과 드라이버 설치로 끝나도록 처음부터 규칙을 지켰고, Postgres일 때는 커넥션 풀과 `pool_pre_ping`이 자동으로 켜집니다.

### Q10-3. 캐시는 안 쓰나요?
지금은 없습니다. 구 Sales Hub는 브랜드별 번들 캐시와 세대 번호로 무효화를 했습니다. 필요해지면 대시보드 결과를 (브랜드, 기준일, 필터) 키로 캐시하고 업로드·매핑 해석 때 해당 브랜드 캐시를 비우겠습니다. 쓰기가 드물고 읽기가 많은 화면이라 효과가 큽니다.

### Q10-4. 서버를 여러 대로 늘리면 문제가 되는 부분은?
v1의 인프로세스 스케줄러(APScheduler)가 대표적이었습니다. 인스턴스마다 같은 백업이 돌고, 서버리스에서는 아예 안 돕니다. 그래서 v2에서 제거하고 백업은 관리형 DB에 맡겼습니다(D4, D5). 세션은 서명 검증 + DB 조회라 인스턴스 간 공유할 상태가 없습니다. 남는 건 같은 주차를 동시에 재집계하는 경우로, 11절에서 답합니다.

## 11. 동시성과 트랜잭션

### Q11-1. 트랜잭션 경계는 어떻게 잡았나요?
요청당 세션 하나이고(`get_db`), 예외가 나면 롤백합니다. 구 버전은 롤백 없이 닫기만 해서 실패한 트랜잭션이 커넥션에 남을 수 있었습니다.
→ **한계는?** 서비스 함수 안에서 커밋하는 곳이 있습니다. 예를 들어 판매 등록은 주문을 커밋한 뒤 재집계가 따로 커밋합니다. 재집계가 실패하면 원장과 집계가 어긋납니다. 서비스는 `flush`까지만 하고 커밋은 요청 경계(라우터 또는 Unit of Work)에서 한 번 하는 구조가 맞습니다.

### Q11-2. 발주 계획을 두 사람이 동시에 고치면?
낙관적 잠금입니다. 클라이언트가 읽을 때 받은 `version`을 함께 보내고, 서버의 현재 버전과 다르면 409 "다른 사용자가 먼저 수정했습니다"로 돌려보냅니다.
→ **완전한가?** 아닙니다. 지금은 "읽고 비교한 뒤 쓰기"라 두 요청이 동시에 같은 버전을 읽으면 둘 다 통과할 틈이 있습니다. SQLite는 쓰기가 직렬화돼 실제로 겹치기 어렵지만 Postgres에서는 가능합니다. SQLAlchemy의 `version_id_col`을 쓰면 `UPDATE … WHERE id = ? AND version = ?`가 되고, 영향받은 행이 0이면 `StaleDataError`가 나서 원자적으로 막힙니다. 그렇게 바꾸는 게 맞습니다.
→ **왜 비관적 잠금(SELECT FOR UPDATE)이 아닌가?** 충돌이 드물고(월 1회 발주, 담당자 소수), 화면을 열어 둔 채 오래 생각하는 작업이라 잠금을 오래 쥐면 안 됩니다.

### Q11-3. 두 사람이 같은 주차 판매를 동시에 업로드하면?
SQLite는 쓰기 잠금으로 직렬화됩니다. Postgres에서는 두 재집계가 같은 주차의 파생 행을 지우고 다시 쓰다 `(주차, 품목, 창고)` 유니크 제약에 걸릴 수 있습니다. 그러면 무결성 오류 처리기가 409를 돌려주고, 다시 시도하면 멱등이라 결과가 맞습니다. 더 깔끔하게 하려면 주차 단위로 advisory lock을 잡거나 재집계를 큐 하나로 직렬화하겠습니다.

## 12. 테스트와 품질

### Q12-1. 테스트 전략은?
네 층입니다.
- **순수 단위**: 예측 공식, ISO 주차(연말 경계), 엑셀 셀 변환 — DB 없음
- **서비스 + DB**: 파생 집계(멱등, 보존, 결손 데이터), 재고·유통기한·이관, 매출 분석
- **API**: `TestClient`로 앱을 인메모리 호출. 로그인, 쿠키, CSRF 헤더, 권한별 403까지
- **규약**: 제약조건 이름 누락, 대문자 테이블명, 금액 정밀도 한계를 테스트로 강제

그리고 테스트 밖에서, 기능이 끝나면 **시드 데이터로 전 구간을 돌려 숫자가 상식적인지 눈으로 봅니다.**

### Q12-2. 서버를 안 띄우고 어떻게 API를 테스트하나요?
`with TestClient(app)` 블록이 lifespan까지 실행하고 쿠키를 들고 다니므로 로그인 흐름이 그대로 검증됩니다. 포트도 프로세스도 필요 없습니다(P-12).
주의할 점은 설정이 import 시점에 확정된다는 겁니다. 그래서 `conftest.py` 맨 위에서 임시 DB 경로와 시크릿을 환경변수로 넣고, 그 아래에서 app을 import합니다.
→ **TestClient가 못 잡는 건?** 쿠키의 `HttpOnly` 플래그가 실제 브라우저에서 동작하는지, 미들웨어 순서, uvicorn 기동 오류입니다. 그래서 완성 시점에 실제 서버로 한 번 훑습니다.

### Q12-3. 테스트끼리 간섭은 어떻게 막나요?
스키마는 세션 단위로 한 번 만들고, 매 테스트 후 모든 테이블을 외래키 역순으로 비웁니다.
→ **겪은 문제는?** 제약 위반 테스트를 하나 추가했더니 **무관한 테스트 9개가 연쇄로 깨졌습니다.** `pytest.raises(IntegrityError)` 뒤 세션이 실패한 트랜잭션 상태로 남아 정리 픽스처의 삭제가 거부됐고, 남은 데이터가 다음 테스트를 엉뚱한 이유(`UNIQUE constraint failed: brand.slug`)로 깨뜨렸습니다. 정리 픽스처에서 `rollback()`을 먼저 하게 고쳤습니다(P-07). 테스트가 무더기로 깨지면 개별 테스트보다 하네스부터 의심합니다.

### Q12-4. 테스트 DB는 왜 Alembic이 아니라 `create_all()`인가요?
테스트는 마이그레이션 이력이 아니라 **최종 스키마**를 검증합니다. 마이그레이션은 `upgrade → downgrade base → upgrade` 왕복이 깨끗이 도는지 따로 확인했습니다. 다만 이 왕복을 자동 테스트로 만들지는 않았고, CI에 넣는 게 다음 할 일입니다.

### Q12-5. 실패하는 테스트가 5개 있는데요?
네, 2026-10-08 측정 기준 385개 중 380개 통과입니다. 실패는 전부 판매·대시보드 API(`test_sales_api.py`)이고 원인을 확인했습니다.
- 4개: 대시보드 응답을 만들 때 `vars()`를 `slots=True` dataclass에 써서 `TypeError` → `dataclasses.asdict()`나 필드 명시로 고치면 됩니다
- 1개: 매핑 재해석 API가 새 매핑이 있을 때만 재집계하는데 테스트와 문서는 항상 재집계를 기대 → "항상 재집계"로 맞추면 됩니다. 그런데 이걸 고쳐도 같은 테스트가 다음 단정에서 다시 실패합니다. 판매 삭제 후 집계가 남는 별도 버그(Q6-6의 1번)가 있기 때문입니다
→ **왜 실패한 채로 커밋했나?** **[직접 채우기]** 사실대로. 예: "Phase 4c를 다른 PC에서 마무리하며 확인을 놓쳤고, 인계 기록에 원인과 함께 남겨 두었습니다. 그 뒤로 턴이 끝날 때 전체 검증을 강제하는 훅을 만들었습니다."

### Q12-6. 커버리지는?
측정하지 않았습니다. **[직접 채우기: pytest-cov로 측정 후 수치]** 커버리지 숫자보다 "결손 데이터 경로를 탔는가", "정상 경로를 탔는가"를 더 중요하게 봤습니다. P-14와 P-17이 둘 다 커버리지로는 잡히지 않는 문제였습니다.

### Q12-7. 프론트엔드 테스트는?
v1에는 서버를 띄워 200 응답만 출력하는 스크립트가 있었는데 단정문이 없어 실패해도 통과처럼 보였습니다. 그래서 pytest로 대체했습니다. 화면 E2E는 v2 프론트(Phase 5) 이후 과제이고, 지금은 reviewer 에이전트가 앱을 실제로 조작하며 루브릭으로 채점하는 탐색 테스트로 보완합니다.

## 13. 운영 · 배포 · 개발 환경

### Q13-1. 배포는 어떻게 할 계획인가요?
컨테이너 하나 + 관리형 PostgreSQL입니다. 설정은 전부 환경변수(`EIBE_` 접두어)이고, 배포 때 `alembic upgrade head`를 먼저 돌립니다. 로드밸런서는 무인증 `/api/system/health`를 봅니다. 백업은 관리형 DB의 자동 백업과 시점 복구에 맡깁니다. **[직접 채우기: 실제 배포 여부]**

### Q13-2. v1 데이터를 v2로 어떻게 옮기나요?
아직 이관 스크립트는 없습니다. 만든다면 테이블별 매핑(대문자 → 소문자, `ORDER_DB`+`MONTHLY_ORDER_PLAN` → `monthly_order_plan`, `SALES_HISTORY`+`OUTFLOW_HISTORY` → `weekly_metric`), 금액은 `Decimal(str(float))`, 문자열 날짜는 엑셀 파서와 같은 규칙으로 파싱하고, 이관 후 품목별 재고·금액 합계를 양쪽에서 비교해 검증하겠습니다.

### Q13-3. 로그와 모니터링은?
v1은 전부 `print()`였습니다. 지금은 표준 `logging`에 요청 ID를 붙입니다. 미들웨어가 요청마다 ID를 만들어 `ContextVar`에 넣고, 로그 필터가 모든 줄에 찍고, 응답 헤더 `X-Request-ID`로도 돌려줍니다. 사용자가 오류 화면의 ID를 알려주면 그 요청의 로그를 바로 찾을 수 있습니다. 지표 수집과 알림(APM)은 아직 없습니다.

### Q13-4. 한국어 Windows에서 겪은 문제는?
세 번 겪었습니다.
- `alembic.ini`에 한글 주석을 달았더니 모든 alembic 명령이 `UnicodeDecodeError: 'cp949'`로 죽었습니다. configparser가 로케일 인코딩으로 읽기 때문입니다(P-03)
- 그 규칙을 적어 놓고도 `requirements.txt`에 한글 주석과 em dash를 넣었다가, 새로 클론한 PC에서 pip 설치가 첫 줄부터 죽었습니다. 그 뒤 `python -m alembic`도 실패했는데 별개 문제가 아니라 **설치가 안 됐기 때문**이었습니다. 원인 하나가 무관해 보이는 증상 두 개로 나타났습니다
- 한글 로그가 깨져 `configure_logging()`에서 stdout을 재설정했는데, **설정 로딩 중 경고**는 그 전에 찍혀서 여전히 깨졌습니다. 어떤 모듈보다 먼저 실행되는 `app/__init__.py`로 옮겼습니다(P-04)

결론은 "외부 도구가 읽는 텍스트 파일(`.ini`, `.bat`, `requirements.txt`)은 ASCII"이고, 파일 안에 그 이유를 적어 뒀습니다.

### Q13-5. "API가 응답하지 않으면 좀비 uvicorn부터 의심한다"는 건?
v1에서 API가 오류 로그도 없이 무한 로딩된 적이 있습니다. 코드를 한참 봤는데 원인은 이전에 비정상 종료된 uvicorn 프로세스가 포트를 잡고 있던 것이었습니다. APScheduler가 종료 시 메인 스레드를 막아 프로세스가 안 죽은 경우도 있었습니다(`shutdown(wait=False)`로 해결). 그 뒤로 무응답이면 프로세스부터 정리하는 절차를 스킬로 만들었습니다.

### Q13-6. 여러 PC에서 작업을 어떻게 이어가나요?
`이전현황.md`(인계 기록)와 `STATE.md`(로드맵·결정)를 갱신하고, 시드의 난수를 고정해 어느 PC에서나 같은 샘플 데이터가 나오게 했습니다.
→ **인계 문서가 맞는지 어떻게 아나?** 빈 폴더에 클론해서 문서의 명령을 **한 줄씩 그대로** 실행해 봅니다. 쓴 사람의 PC에는 이미 다 깔려 있어서 문서가 검증되지 않기 때문입니다. 실제로 첫 명령부터 실패했고, 검증 스크립트가 실패를 무시하고 "완료"를 찍는 바람에 다음 단계 실패를 다른 원인으로 오해하기도 했습니다(P-16).

## 14. AI 활용 개발

### Q14-1. AI를 어떻게 활용했나요?
AI에게 코드를 맡기되 **검증 장치를 먼저 만들었습니다.**
- 메인 세션이 PM 역할을 하며 요구를 계약서로 바꿉니다. 계약서에는 목표, 손댈 수 있는 파일 범위, 검증 가능한 수용 기준(업무 규칙 숫자 그대로), 범위 밖이 들어갑니다
- 영역별 에이전트(front·back·data)가 구현합니다. 작업 크기(S/M/L)에 따라 절차가 다르고, 스키마 변경 같은 L 작업은 제 승인을 거칩니다
- 훅이 위험 명령(강제 push, `reset --hard`, 운영 DB 삭제 등)을 차단하고, 파일 수정 직후 정적 검사를, 턴이 끝날 때 전체 검증을 돌립니다. 실패하면 턴을 끝내지 못하고, 세 번 연속 실패하면 저에게 보고합니다
- 리뷰와 감사는 **빌더와 다른 모델 계열**(Codex)이 합니다. 같은 모델은 같은 맹점을 공유하기 때문입니다

### Q14-2. AI가 만든 코드를 어떻게 믿나요?
믿지 않고 측정합니다. "타입을 바꿨다"고 쓰기 전에 실제로 값을 넣어 봅니다. P-02(금액 정밀도)와 P-14(음수 수요)가 둘 다 그렇게 발견됐습니다. 그리고 AI든 사람이든 실수한 기록을 patterns.md에 남깁니다. ASCII 규칙을 적어 놓고 스스로 어긴 P-03 후일담처럼요.

### Q14-3. 본인이 한 것과 AI가 한 것을 구분해 주세요.
**[직접 채우기]** 실제 비중대로 말한다. 과장하면 다음 질문("이 함수 화이트보드에 써 보세요")에서 무너진다. 구분 축 예시:
- 내가 정한 것: 업무 규칙과 숫자, 무엇을 버릴지(D1~D17의 대안 비교), 검증 기준
- 내가 발견한 것: 실데이터 실행에서 나온 문제와 원인 판단
- AI가 한 것: 결정된 설계의 구현, 테스트 작성, 포팅

### Q14-4. 이 코드를 직접 설명할 수 있나요?
이 다섯 개는 화이트보드에 그릴 수 있게 연습해 둔다.
1. 예측 공식과 예시 숫자 (Q4-1)
2. 파생 재계산 다섯 단계와 IMPORTED 보존 (README 8.2)
3. 쿠키 + CSRF 요청 흐름 (Q9-1)
4. FEFO 로트 판정 예시 (Q5-2)
5. 이관 탐욕 배분 (Q5-3)

### Q14-5. 하네스에 한계는 없나요?
있습니다. 하네스를 v1 기준으로 만든 뒤 v2를 병합해서, 지금 훅의 검사 경로와 역할별 담당 경로에 `eibe/`가 없습니다. v2 변경을 훅이 검사하지 않습니다. 실패 테스트 5개가 남은 것도 이 공백과 관련이 있습니다. 하네스를 eibe 기준으로 옮기는 게 다음 할 일 목록 3번입니다.

## 15. 협업 · 문서 · 프로세스

### Q15-1. 문서를 어떻게 관리하나요?
역할을 나눴습니다.

- `이전현황.md` — 기기 간 인계. 다음 할 일과 완료 조건

### Q15-2. 커밋 메시지에 "no message"가 많던데요?
v1 시기에 혼자 빠르게 작업하며 생긴 습관입니다. v2부터는 Phase 단위로 커밋하고 메시지에 **무엇을과 왜**를 같이 남기는 규칙을 세웠습니다. 다만 Phase 4c 커밋(`847896c`) 하나가 다시 "no message"로 들어갔고, 실패 테스트도 거기서 들어왔습니다. 규칙이 문서로만 있으면 지켜지지 않는다는 걸 배웠고, 그래서 검증을 훅으로 강제하게 했습니다.

### Q15-3. 기존 결함은 어떻게 관리하나요?
`.squad/verify-baseline.txt`에 현재 알고 있는 결함을 적어 두고, 검증은 그 목록을 제외하고 통과 여부를 봅니다. 고치면 목록에서 지우고, **새로 추가하려면 사용자 승인**이 필요합니다. 결함이 조용히 늘어나는 걸 막는 장치입니다.

### Q15-4. 요구사항은 어떻게 받았나요?
**[직접 채우기]** 누구에게서, 어떤 형식으로. 프로젝트에 남은 흔적: 재고일수 기준(13주 적정), 6개월 뒤 도착분 발주, '시뮬레이션 실행' 버튼 제거, 전자제품의 '보증기한' 치환, 인보이스 → 입고 용어 통일, 발주-생산-인보이스 3단계 매칭 폐기 (`docs/history.md` 7.3, 7.16, 7.17).

## 17. 가상 시나리오 질문

### Q17-1. 주 단위가 아니라 일 단위 예측이 필요하다면?
원장은 이미 `ship_date`를 일 단위로 갖고 있어서 집계 단위만 바꾸면 됩니다. `weekly_metric`과 같은 구조의 일별 집계를 두거나, 주간 수요를 요일 비중으로 나누는 방법이 있습니다. 다만 재고 스냅샷이 주 1회라 일별 재고 흐름은 알 수 없다는 한계가 남습니다.

### Q17-2. 품목과 창고가 100배로 늘면?
먼저 N+1 쿼리를 일괄 조회로 바꾸고(Q10-1), PostgreSQL로 옮기고, 대시보드를 기간 한정 + SQL 집계로 바꿉니다. 재집계는 이미 주차 단위 부분 재계산이라 크게 문제없습니다. 화면은 전체 격자 대신 위험 구간만 먼저 보여주는 식으로 바꿔야 합니다.

### Q17-3. 창고 시스템(WMS)과 실시간 연동하라면?
스냅샷 모델은 그대로 두고 입력 경로만 늘립니다. WMS가 재고를 보내면 스냅샷으로 넣고, 입출고 이벤트를 준다면 이벤트 테이블을 따로 두고 스냅샷을 주기적으로 검증용으로 씁니다. 중요한 건 "원장 하나, 나머지는 파생" 원칙을 유지하는 겁니다.

### Q17-4. 다른 회사도 쓰게 하려면(멀티테넌트)?
모든 업무 테이블에 테넌트 키를 넣고, Postgres 행 수준 보안(RLS)이나 쿼리 필터로 격리합니다. 업무 규칙 상수(13주, 6개월, 9주, 임계값)는 테넌트별 설정으로 빼야 합니다. 지금은 모듈 상수로 한 곳에 모여 있어 옮기기 쉽습니다.

### Q17-5. 경영진이 "AI 예측을 넣자"고 하면?
먼저 백테스트로 현재 방식의 오차를 측정해 기준선을 만들고, 같은 데이터로 후보 모델을 비교하겠습니다. 이기는 경우에도 발주 근거를 설명해야 하므로 통계 예측을 기본으로 두고 모델 예측을 참고값으로 나란히 보여주거나, 모델이 가중치를 제안하고 사람이 승인하는 방식을 제안하겠습니다. "ML 금지"는 고집이 아니라 설명 가능성이라는 요구사항에서 나온 결정이라, 그 요구를 만족하면 바꿀 수 있습니다.

### Q17-6. 리드타임이 품목·공급사마다 다르면?
지금은 6개월(`ORDER_LEAD_MONTHS`)과 24주(`DEFAULT_HORIZON_WEEKS`)가 상수입니다. 품목(또는 공급사) 속성으로 옮기고, 시뮬레이션 길이와 항공 경보 시점도 그 값에서 계산하게 바꿉니다. 함수가 이미 인자로 받고 있어서 호출부만 바꾸면 됩니다.

### Q17-7. 환율이 크게 움직이면 자산 평가는?
그래서 마스터 단가가 아니라 **입고 때 실제 결제한 원화**로 평가합니다. 환율 변동은 입고 시점의 원가에 이미 반영됩니다. 평가 시점 환율로 다시 보고 싶다면 그건 별도 지표(환산 평가액)로 나란히 보여주겠습니다.

### Q17-8. 업로드가 중간에 끊기면?
500행마다 flush하고 마지막에 한 번 커밋하므로, 커밋 전에 끊기면 그 업로드 전체가 롤백됩니다. 판매 적재 커밋 후 재집계 전에 끊기면 원장은 들어가고 집계만 낡습니다. 이 경우 매핑 재해석이나 다음 업로드의 재집계로 회복되지만, 원래는 한 트랜잭션이어야 합니다(Q11-1).

### Q17-9. 다시 인터넷 없는 PC에서만 돌려야 한다면?
연결 문자열을 SQLite로 두면 그대로 돕니다. 화면의 외부 의존성은 Chart.js CDN과 Google Fonts 두 개라 로컬 파일로 바꾸면 됩니다. 백업은 관리형 DB에 맡겼기 때문에 그 경우엔 파일 백업을 다시 만들어야 하는데, 인프로세스 스케줄러 대신 OS 작업 스케줄러로 돌리겠습니다.
